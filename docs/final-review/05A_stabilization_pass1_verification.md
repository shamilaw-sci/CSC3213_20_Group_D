## H01 — PARTIAL

**Contract traced:** Web `POST /api/auth/verify-otp` and mobile `verifyOtp(email, otpCode)` send `{email, otpCode}`. Route → `verifyOtpController` → `verifyOtp` → OTP repository and transactional user/profile creation. `createUser` returns `verification_status`; patients are `approved`, professionals `pending`. Response is HTTP 201 `{success,message,data:{approvalPending,user,profile}}`. The controller sets a session for patients/approved accounts, not pending professionals. Web shows the role-specific message on login; mobile alerts and returns pending professionals to login. Web/mobile login send `{email,password}` to `POST /api/auth/login`; controller → `login` → `findUserByEmail`, then profile repository, session save and HTTP 200 `{success,message,data:<session user>}`. Pending/rejected/non-approved professionals receive 403 before password comparison. `GET /api/auth/me` now runs `isAuthenticated` before `getMeController`; no session returns 401, inactive or non-approved professional session returns 403 and is destroyed, and an active eligible session returns 200 `{success,message,data:<session user>}`. Web hydration consumes that shape. Approved professionals can pass the new status checks; normal patient OTP/login remains supported.

**Verified limitation/regression:** `auth.service.js` previously rejected any user with `verification_status='rejected'`. The new condition checks status only when `role !== 'patient'` (`login`, around line 224), so a patient row marked `rejected` can now authenticate with a valid password. Normal patient registration creates `approved`, so this needs a demo-row regression test and a source correction before H01 is called fully resolved. The patient OTP flow also creates a session, while web copy says “You can sign in now”; this is harmless but can cause an unnecessary second login. No live patient/doctor/session test was run.

**Tests executed:** backend syntax PASS; frontend ESLint/build PASS; six changed mobile files parsed PASS. No runtime/database auth test. **Further source modification required:** yes, restore explicit rejection semantics without changing ordinary patient onboarding; add role/session regression tests.

## H04 — PARTIAL

**Paths reviewed:** `backend/src/modules/appointment/{appointment.routes.js,appointment.controller.js,appointment.repository.js}`, `backend/src/modules/patient/{patient.routes.js,patient.controller.js,patient.service.js,patient.repository.js,consent.service.js,consent.repository.js}`, `frontend/src/{components/doctor/PatientNotesModal.jsx,pages/doctor/ConsultationPage.jsx}`.

**Contract traced:** Doctor UI `GET /api/appointments/patients/:patientId/notes` sends no body and consumes `{success,data:notes[]}`. Route requires session/doctor role, then controller checks a same-day appointment belonging to that patient and doctor. Only then it calls `patientService.getMedicalRecords(patientId, sessionUser, activeAppointment.id)` and filters `record_type === 'consultation'`. That service queries patient records newest-first, reads `locked_categories`, and, when categories are locked, checks `getConsentAccessStatus` for the appointment. The consent service validates patient/doctor/appointment ownership and `in_progress`; repository only returns non-revoked, unexpired grants. Without a valid grant, records matching locked category text are filtered out; a valid grant reveals only its granted categories. The old `getConsultationNotesByPatientId` still contains an unfiltered `SELECT *`, but repository-wide search found no remaining caller. The patient medical-records endpoint and history-summary service use the same filtering service. No other endpoint directly invokes that old unfiltered consultation-note query.

**Limits:** The same-day appointment gate accepts `scheduled`, `confirmed`, or `in_progress` (`getTodayActiveAppointmentByPatientAndDoctor`), not exclusively a consultation already in progress. That behavior predates Pass 1; temporary grant validation is stricter (`in_progress`). If multiple appointments exist for the same patient/doctor today, the query chooses the latest `scheduled_at`, which may not be the grant-bearing in-progress appointment; this needs a fixture test. Category matching is substring-based over record text, not an explicit record-category field. Most importantly, `is_confidential` is not independently checked by this policy; see the evidence section below. A confidential record with no matching locked category remains visible to an authorized doctor during the appointment. Therefore H04 cannot be marked fully resolved without a team policy decision. No live unlocked/locked/granted/expired/no-appointment test was run.

**Tests executed:** backend syntax PASS. No consent integration test. **Further source modification required:** not to preserve the existing category policy; possibly yes after the team defines the independent meaning, if any, of `is_confidential` and the intended appointment-status gate.

## `is_confidential` evidence and policy question

**A. Where set?** The doctor consultation form (`frontend/src/pages/doctor/ConsultationPage.jsx`, around lines 1328, 1528 and 6566) initializes a false checkbox and submits `is_confidential`; `ConsultationNotesModal.jsx` has another checkbox. `addConsultationNotesController` reads the body flag and `appointment.repository.createConsultationNote` inserts it into `medical_records`, defaulting nullish input to false. The available incremental migrations do not define that column; the database schema provenance still needs a baseline artifact.

**B. What reads/checks it?** `patient.repository.getMedicalRecords` selects it; the older appointment repository `SELECT *` also returns it. Patient web/mobile record screens, doctor consultation views, and `PatientLookupPage` display confidentiality badges/warnings. The doctor form says “Apply existing Care4U privacy restrictions.” Repository/service/consent searches found no branch that authorizes or excludes records based on `is_confidential`.

**C. Current semantics:** In the checked paths it is **metadata and UI warning**, not an independent authorization restriction. The actual doctor filter checks patient `locked_categories` matched against record text, and temporary category grants.

**D. Same concept?** Evidence does not establish that. A clinician-set boolean on a record and patient-selected string categories/grants are different data structures and can disagree. The form copy suggests a privacy intent, but no mapping to a locked category or grant exists. Team confirmation is required; do not infer a rule from the label.

**E. If every `is_confidential=true` record were hidden without explicit consent:** Authorized doctors would lose visibility to records now visible under no locks or unrelated locks, including potentially their own notes. Existing grants authorize named categories, not a generic confidential flag, so there is currently no defined way to reveal such a record. Patient-self visibility, emergency access, clinical continuity, and existing-data migration would also need explicit policy. An automatic filter could create a safety regression.

**Recommendation:** H04 remains **PARTIALLY RESOLVED**: the parallel notes route now reuses the established category policy, but independent confidentiality semantics and the scope of “active consultation” require team confirmation before claiming a full privacy fix.

## Exact manual integration steps for an isolated demo environment

Use a disposable Care4U database and a test mail inbox/sink only; never run these against production or real patient records. Configure the backend to point to that database and the web/mobile clients to that API. Seed unique demo patient, approved doctor, pending professional, rejected professional, deactivated professional, admin, two same-day appointments, and two health articles (one draft, one published). Keep separate cookie jars/sessions for each role and verify the database values before starting.

1. **Auth:** Register a fresh demo patient and doctor; use their test-inbox OTPs with `POST /api/auth/verify-otp` `{email,otpCode}`. Expect patient HTTP 201 with `approvalPending:false` and `GET /api/auth/me` HTTP 200; doctor HTTP 201 with `approvalPending:true`, no usable session, and `/me` HTTP 401. Patient login and approved-doctor login should each return HTTP 200 and `/me` HTTP 200 with the expected role/profile. Pending and rejected professional login should return HTTP 403; deactivated professional login should return HTTP 403. From an approved-doctor session, change only the **demo** user status to pending, then rejected, and separately `is_active=false`; each subsequent `/me` and a protected doctor endpoint should return HTTP 403 and invalidate the session. Unauthenticated `/me` should return HTTP 401. Also test a demo patient row marked `rejected`: the current code is expected to allow it with a valid password; this is the regression to resolve.
2. **Health content:** Without cookies call `GET /api/admin/health-content`, then repeat with `?status=draft`; both responses should contain only the published fixture. As admin call `GET /api/admin/health-content/admin` (both fixtures) and `?status=draft` (draft only). Without/admin-wrong-role cookies the admin listing should return 401/403. Create/edit/publish/delete a separate demo article via `POST /`, `PUT /:id`, `POST /:id/publish`, `DELETE /:id` beneath `/api/admin/health-content`; verify the response and listing transitions without touching the original fixtures.
3. **Consent/notes:** Give the demo patient a same-day appointment with the approved doctor in `in_progress`. Create one unlocked consultation record and one record whose title/body contains a category such as `diabetes`; set the patient's `lockedCategories:['diabetes']` via `PUT /api/patients/:id/consent` in the patient session. Doctor `GET /api/appointments/patients/:patientId/notes` should show the unlocked record and hide the matching locked record. Request/verify a consent code through `POST /api/patients/:id/consent/access/request` and `/verify` using `{appointmentId}` and `{appointmentId,otpCode}`; obtain the code only through the demo inbox. The doctor notes GET should then show both records. Expire the grant in the **demo** database and repeat: locked record hidden again. Set the appointment to completed/cancelled, or use a doctor without a same-day appointment: notes GET should return 403. Repeat with `is_confidential:true` but no matching locked category to confirm current metadata-only behavior, not to assert intended policy. Compare `GET /api/patients/:id/medical-records?appointmentId=...` under the same conditions.
4. **Reset:** Request reset for a demo account via `POST /api/auth/forgot-password` `{email}`; use the test-inbox link on web and paste the same full link into mobile. Matching ≥8-character passwords should produce HTTP 200 and permit login with the new password. Try a random token and an expired token (expire only the disposable database row): expect HTTP 400 with an actionable screen error. Enter mismatched mobile passwords and verify no API call occurs. Paste a URL without `?token=` and observe the current **known failure**: the full URL is sent as the token and the backend rejects it. Verify the unchanged web reset page independently.
