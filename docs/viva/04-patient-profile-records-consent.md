# Patient profile, records and consent — Stage 4A

2026-11-14. Baseline `b09bfd0`; see [stage report](../review/STAGE4A.md), [catalog assessment](../review/SUPABASE_CATALOG_ASSESSMENT.md) and [existing auth foundation](02-authentication-and-access.md). This guide explains the reviewed paths. Large Patient/Doctor files remain **partial**: unrelated clinical CRUD, appointment scheduling, prescriptions, emergency, laboratory, AI implementation and photo-storage policy are not certified complete.

## The workflow and identities

1. Express session middleware loads a session. `isAuthenticated` rechecks account active/approval/role state; `authorize` checks role. Neither the client role argument nor a user-supplied patient ID grants access.
2. `users.id` identifies an account. `patients.id` and `doctors.id` identify profiles linked through `user_id`. The web profile resolves `/api/auth/me`; records and mobile use `profile_id`, with no fallback to the account UUID. The patient route guard compares the requested profile to the session profile. Consent service additionally resolves the owning profile from account ID. Missing/duplicate/stale profile-link policy is not globally redesigned.
3. Owning patients can read their profile/history and edit only name, blood group and emergency-contact fields. Profile save and privacy switches are separate API writes; cancelling a profile form does not undo privacy changes already saved.
4. Doctors need an appointment assigned to themselves and that patient, with status `in_progress`. This check now also runs inside the medical-record service, including callers such as the summary and previous-notes paths, before record payload loading. A completed consultation workspace may still show its allowed context, but cannot use this active-record/consent path.
5. Category locks filter `medical_records` by case-insensitive phrase matching across type/title/description/chief complaint/diagnosis/treatment. A matching record needs **every matched locked category** in the active grant. Owners see their full history. Missing grant or grant-status error leaves matched records hidden. Nonmatching text is not a clinical classification guarantee; `is_confidential` is not a separate backend authorization gate. Those limitations remain explicit.

## Complex logic: replacement, verification and races

`withPatientTransaction(patientId, work)` obtains one client, begins, locks the existing patient row `FOR UPDATE`, runs the callback, commits, and releases. Unexpected failure rolls back before release. A patient-row lock also serializes operations when no consent-settings row exists yet. Settings replacement, OTP replacement and verification all use this lock and pass the same client to their repository calls. In transactional context, appointment lookup uses `FOR SHARE` to hold assignment/status stable during grant mutation. These SQL contracts are source/mock-tested; real PG deadlocks, isolation, commit failure and concurrent interleavings are not claimed tested.

`requestConsentAccessOtp` validates the doctor/context, generates a cryptographic six-digit code and bcrypt hash outside the mutation lock, then rechecks context inside the transaction. It reads valid stored locks; returns an existing active grant without email, or invalidates prior unused requests and inserts a replacement. Only after commit does it submit email. A failed response or thrown provider exception invalidates **this request ID**, not a newer replacement. Submission acknowledgement does not prove inbox delivery; concurrent email delivery may be out of order. No OTP/hash is returned to the client. Codes expire after 10 minutes.

`verifyConsentAccessOtp` accepts a six-digit string, validates consultation, then serializes read/compare/consume/revoke/grant on one patient transaction. A wrong code increments attempts; the fifth attempt invalidates the request. Expected errors are returned from the transaction callback as error values, so attempt changes commit **before** the service throws the HTTP error. Throwing inside that callback would roll back counters and permit unlimited retry. Unexpected SQL failures still throw and roll back.

A correct comparison is followed by a guarded consume: unused, not invalidated, fewer than five failures, and expiry later than `clock_timestamp()`. Wall-clock time matters because `NOW()` is frozen at transaction start and bcrypt may finish after expiry. Only a successful consume can revoke an old grant and insert a 15-minute replacement, all atomically. If grant creation fails, consumption/revocation roll back too. Grant queries require the same patient/doctor/appointment, no revocation and a future expiry. The grant is an authorization check on each backend fetch, not permanent permission or a claim that already-seen data can be recalled.

Revocation presently means superseding active grants during successful verification. There is no patient-operated revoke endpoint, no automatic cancellation of grants when lock settings change, and no global revoke-on-profile/role-change policy implemented here. Settings changes are serialized but preserve that existing policy. These are open product/security questions; do not promise instant revocation in UI.

## Database relationships and limits

The supplied PostgreSQL 17.6 catalog supports users→patients/doctors account links; appointments→patient/doctor; medical_records→patient/doctor/appointment; consent requests→patient/doctor/appointment; grants→request/patient/doctor/appointment. Request/grant arrays, timestamps, attempt count, used/invalidated/revoked fields and UUID defaults exist. consent_settings has unique patient_id, supporting ON CONFLICT; no patient FK was returned for it. No unique active-grant/request constraint was returned; service serialization supplies the intended mutation protocol without a schema migration. Profile user_id uniqueness is not demonstrated except hospitals. Medical type CHECK permits consultation, diagnosis, lab_result, vaccination, other. Public RLS/grants/API exposure is a separate deployment question; the catalog is not a verified restore script.

**Why not trust profile_id alone everywhere?** It is a profile identity, while consent doctor resolution also checks the linked account and appointment; stale/ambiguous links remain a documented broader policy concern.

**Why return an error value from a wrong-code transaction?** To commit the failure count before throwing to the controller. Unexpected SQL failures still roll back.

**Why clock_timestamp()?** A code can expire during hashing/comparison; transaction-start NOW() would not advance.

**Does a green mock test prove locking?** No. It proves invocation/query contracts. Real row locks, isolation, rollback and races need an isolated database later.

**Can the patient cancel a privacy switch using profile Cancel?** No. Each switch is a separate acknowledged save; UI wording states this.

**Does category matching guarantee confidentiality?** No. It can miss diagnoses that lack the exact label, and is_confidential is not a backend lock policy. Clinical classification and revocation rules remain open.
